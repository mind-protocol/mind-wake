== 2. Correctif (durable, pour toutes les salles) ==

a) Le worker reste vivant quand toutes les rooms sont sur Off, s'il reste au moins une room affectée (src/daemon/forks.ts) :
   `if (enabled.length === 0 && !anyRoomAssigned(dataDir)) break;`
   Une room non affectée attend (sleep 1 s) au lieu de sortir. Un On ultérieur la reprend sans redémarrer le worker.
   `forks status` expose aussi `workerNeeded` (une room sur On, ou une room affectée).

b) Une salle présente dans un appel actif répond à chaque message (nouveau module src/daemon/room-call-presence.ts, branché dans assignedTurn) :
   - Présence : la salle est dans un appel si mobile-call-control.sqlite (tenu par le serveur de l'app) contient une ligne avec state='active', last_seen datant de moins de 120 s, et dont les participants contiennent room<N>, room-<N> ou l'id d'un de ses agents. Lecture seule, relue au plus toutes les 2 s.
   - Déclencheurs (callTriggers) : entrées en attente arrivées depuis le début de l'appel, pas encore servies (`oneshot:<id>` absent), qui sont soit d'origine humaine, soit une mention de la salle : @room<N>, @room-<N>, son nom affiché (mot entier, sans casse ni accents, par ex. « Emploi remote »), le nom ou @id d'un de ses agents. Un message d'une autre room (senderFork) ne déclenche jamais rien : pas de boucle entre salles.
   - Cela vaut même si la room est sur Off : enabled.json n'est jamais écrit.
   - Pas de plafond ni d'intervalle pour ces tours : claimOneShot(…, uncapped=true) réserve `oneshot:<id>` sans compter dans le plafond de 30 tours sur 24 h.
   - Aucun doublon : chaque message est réservé avant le tour et ne déclenche qu'un seul tour. Plusieurs messages en attente partent en un seul tour, avec les copies non déclenchantes comme contexte. Le décroché répond à la sonnerie, qui n'est pas un déclencheur : il ne fait pas doublon avec ces tours.
   - Prompt d'une room à un agent : note CALL_NOTE (« tu es dans un appel vocal en cours… réponds brièvement, à l'oral »). Room à plusieurs agents : routage inchangé (agent adressé, sinon hub, sinon premier agent).
   - Hors appel, une room désactivée garde la règle existante : tour unique par message humain, plafond de 30 sur 24 h.
   - Journal : « Room N dans l'appel <id> : tour pour le message … ».

c) Documentation : docs/FORKS.md (section Runtime et contrôles).
